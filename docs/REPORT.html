Engineering Findings & Lessons

Finding 1 — SCP Lockout: Root Account Blocked from Member Account
High

Phase: 5 — Security Baseline Automation

What happened: DenyRootAccountUsage SCP blocked root from performing IAM operations in the member account before the IAM user had AdministratorAccess. Created a catch-22 — IAM user couldn't fix itself, root was blocked by SCP.

Resolution: Temporarily detached SCP from management account console, granted AdministratorAccess to IAM user via root, reattached SCP via terraform apply.

Lesson: Always ensure IAM users have sufficient permissions before deploying root denial SCPs. Document a break-glass procedure. Management account is always SCP-exempt.

Finding 2 — Over-Broad SCP Blocking Terraform Operations
Medium

Phase: 5 — Security Baseline Automation

What happened: guardduty:UpdateDetector in deny list blocked Terraform from updating detector configuration (tags, datasource settings).

Resolution: Removed guardduty:UpdateDetector from deny list. Kept only destructive actions: DeleteDetector, DisassociateFromMasterAccount, StopMonitoringMembers.

Lesson: SCPs should deny the minimum set of actions. Test SCPs in Sandbox OU before applying to Workloads.

Finding 3 — Existing Resources Require Terraform Import
Low

Phase: 5 — Security Baseline Automation

What happened: GuardDuty and Security Hub already existed in member account from Project 1. Terraform attempted to create duplicates.

Resolution: Used terraform import to bring existing resources under Terraform state management.

Lesson: In brownfield environments, always audit existing resources before writing Terraform. Use terraform import, never destroy-and-recreate security services.

Finding 4 — Unicode Character Rejected by AWS SSO API
Low

Phase: 4 — IAM Identity Center

What happened: Em dash (—) in permission set description caused ValidationException from AWS SSO API.

Resolution: Replaced em dash with standard hyphen (-).

Lesson: AWS SSO API only accepts ASCII characters in string fields.

Finding 5 — Security Hub enable_default_standards Conflict
Medium

Phase: 5 — Security Baseline Automation

What happened: After importing Security Hub, plan showed destroy-and-recreate due to enable_default_standards mismatch. SCP blocked the disable operation.

Resolution: Set enable_default_standards = false in config to match existing state. Managed standards separately via aws_securityhub_standards_subscription.

Lesson: After terraform import, always reconcile config with actual state before applying.

Interview Talking Points

1. Why management account is governance-only: SCPs don't apply to the management account itself. Placing workloads there defeats the purpose of the control hierarchy.

2. Why SCPs over IAM policies for guardrails: IAM policies can be modified by account admins. SCPs enforced from above cannot be overridden by anyone in the member account — even the root user.

3. Why delegated admin pattern: Allows security tooling to be centrally managed without granting management account credentials to security teams. Principle of least privilege at the organizational level.

4. Why remote state with locking: Prevents concurrent Terraform runs from corrupting state. S3 versioning allows rollback. DynamoDB provides atomic locking.

5. What the SCP lockout taught you: Always define a break-glass procedure before enforcing root denial. The management account's SCP exemption is the recovery path — document it before you need it.
